How string-set families fit

tonal-guitar / Shape Workbench design proposal · draft
### Shape Workbench — data model, export format and app shape
Companion to the screen mockups. Everything here is additive and backwards-compatible with the v0.2.0 registry; nothing changes how applyChordShape or buildFrettedScale place notes.
### 1. What the app is
A local-only authoring tool for the shape registries. It reads the live registry (so it is always in sync with src/data/* ), lets you create and edit chord shapes, arpeggio shapes and scale shapes as movable interval templates authored at a chosen root , links them to each other and to Tonal chord/scale types, and writes a changeset file that a terminal command merges back into src/data/*.ts .
Board — the CAGED grid (chord type × C·A·G·E·D). Empty slots are library gaps you can create straight into. Tabs switch the same grid to arpeggios and scale boxes.
Shapes — the editor: fretboard with note / root / finger / barre / mute tools, live checks from audit.ts , Tonal detect identification, preview at other roots, output preview.
Chords — one page per Tonal chord type: its five CAGED slots, arpeggio slots (derived vs stored), other voicing families, scales containing it, tags.
Graph — relationships (chordType, parentShape, arpeggio-of, same-position) drawn in CAGED lanes so gaps line up; force layout as an alternative.
Export — the changeset review, diff per change, the JSON file, and the merge command.
Why a separate app and not /admin . The docs site is output: "export" — it can never write to disk, which is why the existing /admin editor can only copy TS to the clipboard. The Workbench is a Vite + React app in packages/shape-workbench , linked with file: like fretboard-ui , with a tiny dev-server plugin that writes .workbench/changeset.json . It reuses fretboard-ui ( Fretboard , FretboardEditor , cellsToScaleShapeStrings ) and the pure shapeLibraryUtils.ts / shapeDetailUtils.ts from the site (extracted to packages/shape-catalog so both consumers share them). /admin is retired once the Workbench covers it.
### 2. Data model additions (src/shape.ts)

### Voicing family — one new value
VoicingFamily gains "triad" for closed three-note voicings on a string set. stringSet and inversion already exist (inversion is 0 on every shape today); triads are the first data to populate them, and the board's "Columns" control chooses which field is the column key (CAGED position · string set · inversion). The "extended" value already in use is added to the documented union.
### Barre fret origin — fix, not addition
Movable shapes store Barre.fret as an offset from the grip base; open shapes store absolute frets. Nothing in src/ reads the value, so the editor is the first real consumer. Proposal: define Barre.fret as an offset from baseFret , normalise open-chords.ts in the merge, and add a barre-fret-origin audit warning. applyChordShape additionally passes fingers and barres through on Fingering so grips round-trip through the build engine.
### 3. Arpeggios: a third registry, same shape type
Structurally an arpeggio shape is a ScaleShape — strings: (string[] | null)[] already allows one or more intervals per string, so a sweep form is just [["1P"],["3M"],["5P"],["1P"],["3M"],["1P"]] , and buildFrettedScale , walkShape , inferShapeContext and checkScaleBuildLoss work unchanged. What's missing is a place to keep them without polluting all() (which modeShapes and inferShapeContext enumerate unfiltered).
export interface ArpeggioShape extends ScaleShape {
chordType: string; // required here — an arpeggio always outlines a chord
fingers?: (number | null)[][]; // per-string, parallel to strings[]
chordShape?: string; // the grip this arpeggio belongs to, e.g. "E Shape m7"
overrides?: string; // core entry replaced by this (teacher) version
}
export const arpeggioShapes = { get, all, names, add, remove, removeAll, query({ chordType, system, cagedPosition, tags }) };

### Three tiers per slot
Derived is what exists today: arpeggioFromShape filters a scale box. Which box is a rule, not a guess — the chord-scale rule : the chord type picks the scale (major/maj7 → major, minor/m7 → minor (aeolian; dorian as the alternate to decide), 7 → mixolydian, m7b5 → locrian), and the chord form's root string picks the box in that scale frame whose rootString matches, via relabelShapeToScale(box, scale) . For E Shape m7 at A that is Em Shape (frets 4–8); for E Shape 7 it is the A-Shape geometry relabeled to A mixolydian (frets 4–8, root on the low E). Mode boxes that are not registered today (mixolydian, dorian, locrian, …) are derived on demand first and seeded as first-class entries with cagedPosition + quality in phase 3 — the PLAN.md deferral that relabelShape already supports. Core is a derived result promoted to a stored shape with fingering, tags and parentShape , shipped in src/data/caged-arpeggios-*.ts . Override is a teacher's version of the same slot: a normal stored shape carrying overrides and a teacher: tag; a consumer opts in by registering it, and the core remains its parent. The editor shows the core as ghost notes while an override is edited and reports the diff.
Intervals are stored in the chord frame ( 1P 3m 5P 7m ) — the editor converts from a parent scale's frame when you promote a derived arpeggio, and parentShape records where it came from. arpeggioFromShape keeps returning parent-frame notes for derived results; stored shapes are the curated tier on top, which is exactly the split issue #30 asked for (sweep forms are "the one family not derivable from scale positions").

### 5. Export format and merge command
The app writes one JSON changeset , not TypeScript. TypeScript is generated by the merge script so formatting, identifier naming ( CAGED_CHORD_EM , EXT_CHORD_A_7SHARP9 ) and registration order live in one place — the current /admin TS-template approach has to be re-taught every field.
{
"$schema": "tonal-guitar/changeset@1",
"tuning": ["E2","A2","D3","G3","B3","E4"],
"version": "0.2.0", // registry version the edits were made against
"changes": [
{ "op": "add", "kind": "chord" | "arpeggio" | "scale", "file": "caged-chords-minor", "shape": { … } },
{ "op": "update", "kind": "chord", "name": "A Shape Major", "patch": { … } },
{ "op": "remove", "kind": "chord", "name": "…" }
]
}
npm run shapes:merge -- .workbench/changeset.json (a script under scripts/ , no new dependencies):
Validates every shape with the audit; refuses on errors, prints warnings.
Refuses version drift (the file was authored against a different registry) unless --force .
Writes add changes as constants into the target src/data/<file>.ts (creating it, with the registration block), applies update patches field-by-field to the existing constant, and never touches caged-scales-minor.ts / pentatonic-minor.ts (computed files).
Wires new files into src/index.ts after their parentShape file, and bumps the hard-coded count assertions in data.test.ts / index.test.ts .
--check is a dry run; --out prints the generated TS for a single change (the "Copy TS" button uses the same generator in the browser).
### 6. Movable shapes: authoring at a root
You author on a concrete fretboard — "E Shape Minor at A" — and the app stores intervals, not frets: each placed note becomes intervalFromTo(rootPc, notePc) , the lowest string carrying 1P becomes rootString , and the barre's fret becomes an offset from the lowest fretted fret. Changing "Author at root" re-renders the same template elsewhere; the "At other roots" strip is applyChordShape at C/D/E/G/A with open strings disabled, so you see immediately where the form gets tall. Marking a root is what makes the shape movable — without a 1P the editor refuses to save.
Open-string shapes come later: the same editor with Open strings on, movable: false , and canonicalRoot set to the authoring root. Alternate tunings are the same again with the tuning picker unlocked and tuning recorded on the shape.
