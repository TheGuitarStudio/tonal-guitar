# Shape Workbench — Product Context Research

## 1. Product Alignment

**Assessment: Strong.** The feature closes a gap that PLAN.md never fully anticipated (it was written for a math/data library, not an authoring UI) but that emerged organically through three shipped site features (`shape-visual-audit-library`, `shape-detail-panel`) and is now explicitly tracked as GitHub **issue #161** ("Shape Workbench: shape authoring app + shared read-only docs Shape Library UI"), opened 2026-08-30 with a `feature-spec` label, already referencing #57/#66/#58/#30 — i.e., this research task is formalizing an issue that already exists on the tracker.

- `docs/PLAN.md` has no "workbench" phase; the closest anchor is **Epic 8 (Documentation)**, specifically Task 8.3 (interactive `site/` experiments page, DONE) and Task 8.4 (GitHub Pages deploy, DONE). The plan's Epic 8 predates the docs site's evolution into a full "Guitar Lab" + Shape Library, so the workbench is a *new* epic-level effort layered on top of shipped doc infrastructure, not a phase substitution.
- `docs/design.md` (original API design, pre-dates the site entirely) lists open question #2: *"How to handle open strings in movable shapes? ... Are these the same 'shape'?"* — directly answered by raw-idea.md's scope cut ("open strings and alternate tunings later"), and open question #3: *"How to represent barre indicators? (which fret is barred, which finger)"* — directly implicated by the raw-idea's `Barre.fret` redefinition decision.
- `docs/QUESTIONS.md` Q4 (3NPS pattern names vs. mode compatibility, deferred) and the "Pentatonic/Modal same-shape relationship" section of PLAN.md ("registered entries for the other diatonic modes ... no first-class registry entries are seeded") are exactly the kind of registry-completeness gap a workbench would let a human close incrementally instead of hand-writing more `data/*.ts` files — this is the stated "Why" in raw-idea.md.
- CHANGELOG/README show v0.2.0 (2026-08-02) is the last published release; the workbench is unreleased/future work building on top of it, not blocking it.

## 2. Related Specifications (prior features that inform or constrain this one)

Reading `.tonal-guitar/features/*`:

- **`shape-visual-audit-library`** (issue #97, shipped) — built `src/audit.ts` (`checkChordMetadataCompleteness`, `checkScaleMetadataCompleteness`, `checkGeometryMismatch`, `checkFretSpan`, etc.) and the site's `shapeLibraryUtils.ts`. This is the audit engine the workbench should reuse/extend for authoring-time validation (e.g. catching fret-span or geometry mismatches as a shape is edited, before export). Its oversight notes flag known pre-existing data debt (e.g. CAGED majors/R73 shells have span issues, `OPEN_G_DIM`/`OPEN_G_M7B5` mistagged `voicingFamily:"open"`) that a workbench editor will surface and should not silently "fix" without a deliberate decision.
- **`shape-detail-panel`** (issue #139, shipped) — added `ScaleShape.featured`/`ChordShape.featured`, `scalesContainingChord` (in `src/integration.ts`), and the current `site/app/shapes/` component set (`ShapeLibrary.tsx`, `ShapeCard*.tsx`, `FilterBar.tsx`, `shapeLibraryUtils.ts`, `shapeDetailUtils.ts`, `ChordDetailView.tsx`/`ScaleDetailView.tsx`). This **is** the current read-only docs Shape Library the raw-idea says the workbench UI should "improve/replace." Its research review already flagged the exact tension this feature must resolve: *"challenged 'no library work required' and the vagueness of 'visual reorganization pass'"* — i.e., a prior reviewer already anticipated that Shape Library UI work keeps recurring and should be consolidated, which the raw-idea's shared-component plan (`packages/shape-catalog`) directly answers.
- **`minor-quality-shape-relabeling`** (issue #54, shipped) — `src/transform.ts`'s `relabelShape`/`relabelShapeToScale`, which the raw-idea's "chord-scale rule" (chord type → scale → box in that scale frame) depends on directly: *"via `relabelShapeToScale`"* is named explicitly in raw-idea.md's arpeggio design.
- **`arpeggio-chord-shapes-detection-and-fingerings`** (issue #16, shipped) — `src/arpeggio.ts` (`arpeggioFromShape`, `arpeggioFromScale`, `filterChordTones`), curated jazz shells (`jazz-shells.ts`), `ChordShape` harmonic-metadata fields (`chordType`, `inversion`, `voicingFamily`, `stringSet`, `omittedIntervals`, `canonicalRoot`, `baseFret`). Its `deferred.md` filed 10 follow-up issues (#28–#37), several **directly subsumed or consumed** by this feature:
  - **#30** (sweep-picking arpeggio shapes) — listed in raw-idea's "Related issues"; likely stays deferred/separate (workbench targets CAGED movable shapes first, sweep is 1-note-per-string and explicitly "technique-specific niche").
  - **#36** (grip → ChordShape classification / `inferChordShape`) and **#37** (diatonic-degree arpeggio sugar) are adjacent-but-separate library APIs; not blocking the workbench but worth flagging as related open work in the same subsystem.
- Verified in code: `src/shape.ts` currently has **no `arpeggioShapes` registry** (only `chordShapes` + the base scale registry) and `Barre.fret` has no offset/absolute semantics documented — confirming the raw-idea's claims that these are genuinely new data-model changes, not already-shipped.

**`docs/DOCS_EPIC.md`** only covers Task 8.1–8.4 (README, API docs, experiments page, GitHub Pages deploy) — it predates and does not mention the Shape Library or admin editor at all, meaning this feature effectively opens an unwritten "Epic 9" for the docs site's shape-authoring/library surface.

## 4. User Context

- **Library author/teacher (local, editing mode):** today hand-edits `src/data/*.ts` files directly (e.g. adding a minor CAGED triad means writing a new `ChordShape` literal by hand, per #57/#58's "workaround" language) and validates by running `npm test`/the audit checks. The `/admin` editor (`site/app/admin/page.tsx`) already exists as a `NODE_ENV !== "production"`-gated dev tool built on the shared `fretboard-ui` package's `FretboardEditor`, but only round-trips `ScaleShape` — `ChordShape` (fingers/barres) export is the explicit gap in #66. Workflow needed: browse existing shapes → create/fix one visually → export a reviewable diff (`changeset@1` JSON → `npm run shapes:merge`) rather than committing raw generated TS, so a human still reviews before it lands in `src/data/*`.
- **Docs-site visitor (read-only mode):** already served by `site/app/shapes/` (`ShapeLibrary.tsx`, `FilterBar.tsx`, `ShapeDetailPanel.tsx` with `ChordDetailView`/`ScaleDetailView`), which does faceted filtering, failures-first audit-driven sorting, and a click-through detail panel (identified chord names, related scales, alternate fingerings). This is the UI the workbench will share components with, not build from scratch — most of the pure derivation logic (`shapeLibraryUtils.ts`, `shapeDetailUtils.ts`) is exactly what raw-idea.md proposes extracting into `packages/shape-catalog`.
- **Impact of having vs. not having it:** without it, registry-depth issues (#56/#57/#58) stay perpetually backlogged because closing them means hand-authoring dozens of `ChordShape`/arpeggio literals with correct fret/finger/barre geometry — exactly the kind of tedious, error-prone-by-hand work the existing audit library was built to *catch after the fact* (`checkFretSpan`, `checkGeometryMismatch`, etc.). A visual editor with live audit feedback converts these from "write correct data blind, test, fix" into "see it render correctly before export," directly reducing the error class the audit library exists to detect.

## 5. Scope Boundaries

**In scope (per raw-idea.md + issue evidence), recommended:**
- Chord shapes first (closes #57, and the fingering/barre export gap in #66) — standard tuning, movable/CAGED shapes only.
- Additive, backward-compatible data-model fields (`cagedPosition`, `movable`, `parentShape`, `chordType` on `ScaleShape`, `tags`/`tuning`/`overrides`/`notes`, registry `remove()`) — verified none of these exist yet in `src/shape.ts`, so this is genuinely additive, not a breaking migration, except:
- **`Barre.fret` redefinition** (absolute → offset-from-`baseFret`) is a **breaking migration** of `open-chords.ts`'s existing ~70 shapes — call this out explicitly as a distinct, higher-risk task requiring its own verification pass (likely feeding the existing audit suite's `checkGeometryMismatch`/`checkFretSpan` checks as regression gates), not bundled silently into "add new fields."
- `arpeggioShapes` as a genuinely new third registry (confirmed absent in code) — closes #58's "no first-class seeds" complaint via the derive→core→override tier model.
- Shared UI extraction (`packages/shape-catalog` or equivalent) reusing the **already-existing** `packages/fretboard-ui` (`FretboardEditor`, `Fretboard.tsx`, cell-model helpers already used by both `/admin` and the experiments pipeline) — this substantially de-risks the "one UI investment" premise since the rendering primitive already exists and is shared; the *new* shared piece is the Shape Library's filter/detail/catalog logic (`shapeLibraryUtils.ts`/`shapeDetailUtils.ts`), which currently lives site-local.
- `npm run shapes:merge` terminal command + `changeset@1` JSON export contract — new, no prior art in the repo.

**Out of scope (confirm explicitly, per raw-idea + issue evidence):**
- Auth for a deployed editing mode (raw-idea: "auth itself is out of scope," architecture just shouldn't preclude it later).
- Open strings and alternate tunings for authored shapes (raw-idea: "later"; also echoes design.md's unresolved Open Question #2).
- Sweep-picking arpeggios (#30 — separate issue, no canon yet).
- Full mode-box seeding for all diatonic modes/harmonic/melodic minor beyond CAGED+pentatonic (PLAN.md: "no first-class registry entries are seeded," QUESTIONS.md Q4 — stays deferred; workbench should make this *possible* to fill incrementally but doesn't need to seed it as part of this feature). NOTE: raw-idea/canvas phase 3 seeds the mode boxes needed by the chord-scale rule (mixolydian, dorian, locrian…) — reconcile in shaping.
- Adjacent Lab v2 items (#64 URL-state sharing, #65 multi-shape overlay, #67 click-to-play) — separate site/experiments features, different milestone, different page (`site/app/experiments/`, not `shapes/`/`admin/`).
- `inferChordShape` (#36), diatonic-degree sugar (#37), upper-structure arpeggios (#35), non-standard-voicing CAGED classification (#34) — library-API work in the same subsystem but not workbench-UI blocking.

**Dependencies/risks:**
- Does this feature obsolete/absorb open issues? **Yes** — #57, #58, and likely #56 (blues scales, same "registry depth" milestone, same fill-the-gap pattern) become *achievable via the workbench* rather than needing separate hand-authoring PRs; #66 is essentially *this feature's* chord-editor sub-task already filed. Recommend closing #66 into the workbench's tracked scope (issue #161) rather than treating it as independently completable, since the raw-idea's export design (finger/barre → `ChordShape` → changeset JSON) is the same deliverable.
- Risk: the site is `output: "export"` (static) — raw-idea already identifies this correctly as the reason a separate local app package is needed (site literally cannot write files). This is validated by the current `/admin` page's `NODE_ENV === "production" ? notFound()` guard, i.e. the existing partial editor already works around the same constraint by disabling itself in the deployed build rather than truly separating concerns — the workbench's "separate app package" decision is a real architectural upgrade over that pattern, not just nice-to-have.
- Risk: known pre-existing data debt from the audit library (span issues on CAGED majors/R73 shells, `OPEN_G_DIM`/`OPEN_G_M7B5` mistagged, `jazz-shells.ts`'s 16-variant vs. correct-8 shells discrepancy explicitly named in raw-idea.md) will surface immediately once shapes are rendered/edited visually — scope the first workbench pass to *not* silently auto-fix these; treat them as separate, tracked corrections (the shells fix is already an explicit raw-idea decision item, so at least that one is in-scope).
